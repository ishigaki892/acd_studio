# AtCoder Studio の使い方

入れ方と、はじめの一歩は [README](../README.md) にあります。ここでは、機能ごとの使い方を書きます。

## 画面の配置

- 左端：アクティビティバー。「エクスプローラー」（⇧⌘E）・「検索」（⇧⌘F）・「実行とデバッグ」（⇧⌘D）・「コンテスト」（旗。[コンテストの提出状況](#コンテストの提出状況)）で、左のサイドバーの中身を切り替えます。いま出している中身のアイコンをもう一度押すと、サイドバーを閉じます。下端の歯車は設定
- 左：サイドバー（ファイル一覧など。⌘B で表示を切り替え）
- 上：ボタンの列（問題の選択欄、「実行」「サンプルテスト」「ランダムテスト」「対話テスト」「デバッグ」「提出」）
- 中央：エディタ（タブ）
- 右：問題文。右下：「提出結果」
- 下：「実行ログ」「テスト結果」「エラー一覧」「デバッグコンソール」「履歴」のタブ

ペインの境目はドラッグで動かせます。窓は 800 × 500 より小さくはなりません。

## 作業領域と信頼

- 問題を置くフォルダを「作業領域」と呼びます。「フォルダを開く」（⌘O）で選びます。次に起動したときは、同じフォルダとタブが開きます。
- 初めてのフォルダでは「このフォルダを信頼しますか」と聞かれます。ビルドや言語サーバー（rust-analyzer・clangd・basedpyright）は、フォルダの中の設定（`build.rs`・`.cargo/config.toml` など）を通してコードを動かすことがあるためです。
  - 「信頼する」：すべての操作ができます。次からは聞かれません。
  - 「信頼しない」：ファイルの読み書き・問題の表示・パッケージを作ることはできますが、実行・テスト・デバッグ・言語サーバー・提出はできません。次からは聞かれません。ファイル一覧の上の「信頼する…」で、信頼し直せます（もう一度、確認の画面が出ます）。

## ファイル一覧

- 見出しの「＋」で新しいファイル、その隣のボタンで新しいフォルダを、選んでいるフォルダに作ります。
- 右クリックのメニュー：ファイルは「名前の変更」「削除」、フォルダは「新しいファイル」「新しいフォルダ」「名前の変更」「削除」。Esc で閉じます。名前の変更では、大文字・小文字だけを変えることもできます。
  - 削除はゴミ箱に移します（フォルダは、中のファイルの数が確認の画面に出ます）。リンクは、リンク自体を消します（リンクの先は残ります）。
  - フォルダの名前を変えると、中のファイルのタブとブレークポイントも付いてきます。
  - 実行・テスト・デバッグ・問題を作っている間は、フォルダの名前の変更・削除はできません。
- Finder などで作業領域の中身を変えたときは、IDE の窓に戻ると一覧が読み直されます。
- フォルダの中身の左の縦の線で、深さが分かります。カーソルを乗せると、その項目のフォルダの線が濃くなります。

## 検索

- アクティビティバーの虫眼鏡（⇧⌘F）で、サイドバーが「検索」になります。エディタで 1 行の中を選んでいれば、その文字を探します。
- 入力をやめて少しすると探します（Enter ですぐ）。右のボタンで、大文字と小文字を区別する（Aa）・単語単位（ab）・正規表現（.*）を切り替えます。正規表現の書き方は Rust の `regex` クレートのものです。
- 結果はファイルごとにまとまります。行を押すと、エディタのその場所へ移ります。
- 探す前に、保存していないタブを保存します（検索は保存してある中身を見ます）。
- 1 行ずつ探します（行をまたぐ当たりは探しません）。`.git`・`target`・`node_modules` のフォルダ、シンボリックリンク、1 MB より大きいファイル、文字のファイルでないものは探しません。当たりは 2,000 件までです。
- 置換：入力欄の左の「▸」で置換の欄を開きます。「すべて置換」か、ファイルの行の「置換」で置き換えます。置き換える前に確認のダイアログが出ます。正規表現のときは、`$1`・`${名前}` で当たりの組を使えます。`$1_x` のように数字のあとに文字が続いても、`$1` は 1 番目の組です。`$` の文字は `$$` と書きます。
  - 探したあとで変わったファイル（保存していなかった編集を、置換の前に保存したものも含む）は置き換えません。もう一度探してから置換してください。
  - 置き換えたあと、「置換を元に戻す」で戻せます。戻せるのは直前の置換だけで、次の置換・フォルダの開き直し・アプリの終了までです。置換のあとで変えたファイルは戻しません。

## 問題とコンテスト

### コンテストを作る

1. ファイル一覧の見出しの「⤓」を押し、コンテスト ID（例：`abc480`）を入れて「作る」（または Enter）を押します。言語（Rust・C++・Python）は、設定の画面の「問題文」の「問題を作るときの言語」です。
2. 問題の一覧を読み、問題を 1 問ずつ取って、作業領域の直下に次を作ります。進み具合（例：「3 / 7：abc480_c」）と、問題ごとの結果が出ます。

   ```
   abc480/
     .cargo/config.toml    ← ビルドの置き場所（target）を、コンテストの中で共有する
     abc480_a/
       Cargo.toml          ← 名前は問題 ID（数字で始まるなら p_ を付ける）、edition 2024、雛形の依存
       src/main.rs         ← 雛形
       test/sample-1.in    ← サンプル
       test/sample-1.out
       …
       test/input.txt      ← 「実行」の標準入力（入力例 1）
       test/compare.json   ← 比べ方と制限（問題の時間の制限＋500 ms、メモリの制限。誤差の書き方があれば float）
     abc480_b/
     …
   ```

   C++ を選んだときは、`.cargo/config.toml` の代わりに `.clang-format` を置き、問題ごとに次を作ります。

   ```
   abc480/
     .clang-format         ← 整形の書き方（LLVM の書き方で、字下げ 4）。書き換えてかまいません
     abc480_a/
       main.cpp            ← 雛形
       compile_flags.txt   ← ほかのエディタの clangd 用のオプション（IDE の clangd は、IDE が渡すオプションを使います）
       test/…              ← Rust と同じ
   ```

   Python を選んだときは、コンテストのフォルダには何も置かず、問題ごとに `main.py`（雛形）と `test/…`（Rust と同じ）だけを作ります。

3. 終わると、作れた最初の問題の `src/main.rs`（C++ なら `main.cpp`、Python なら `main.py`）が開きます。

- 作っている途中は「止める」で止められます（今の問題を取り終えたところで止まります）。作り終えた問題は残ります。
- すでにあるファイルは上書きしません。結果に「すでにありました」と出ます。ほかの言語のパッケージのフォルダ（例：Rust の `abc480_a/` があるところに C++ で作る）には、ファイルを足さずに知らせます。サンプルを消したときは、もう一度作ると、消したものだけを書き直します。中身を変えたサンプルは書きません（「中身が違うので書いていません」）。
- AtCoder を読むのは「作る」を押したときだけで、1 問ずつ 1 秒あけます。一度読んだ問題はアプリのフォルダに保存し、次からは読みません。
- 開始前のコンテストは、問題の一覧を読めないので作れません。開催中のコンテストは、ログインしていれば作れます（[提出](#提出) のログイン）。

### 1 問だけ作る

- 上の選択欄にコンテスト ID を入れて「一覧」を押し、問題を選ぶと、右に問題文が出ます。
- 問題文の欄の「…」→「この問題を作る」で、その問題のパッケージだけを作ります。言語は、設定の画面の「問題文」の「問題を作るときの言語」です。開いているファイルのパッケージのフォルダ名から問題が決まっているとき（例：`abc480_a/` の中のファイル）は、このボタンは出ません。

### 雛形

アプリのフォルダ（[データの場所](#データの場所)）の `templates/` に、次のファイルを置くと、作る問題がその中身になります。ない方は、IDE の最小の雛形を使います。フォルダは、設定の画面（⌘,）の「テンプレート」の「テンプレートのフォルダを開く」で開けます。

| ファイル | 中身 | ないとき |
|---|---|---|
| `templates/main.rs` | `src/main.rs` の中身 | `fn main() {}` |
| `templates/dependencies.toml` | `Cargo.toml` の `[dependencies]` の中身 | `proconio = { version = "=0.5.0", features = ["derive"] }` |
| `templates/main.cpp` | C++ の `main.cpp` の中身 | `#include <bits/stdc++.h>`、`using namespace std;`、入出力を速くする 2 行だけの `main()` |
| `templates/main.py` | Python の `main.py` の中身 | 空の `def main():` と、それを呼ぶ `main()` |

`dependencies.toml` の例（版は、ジャッジにあるものと同じにします）：

```toml
proconio = { version = "=0.5.0", features = ["derive"] }
ac-library-rs = "=0.2.0"
superslice = "=1.0.0"
itertools = "=0.14.0"
```

- `proconio` の `#[fastout]` を使うには、`features = ["derive"]` が要ります（ジャッジも derive を入れています）。
- 雛形を変えても、すでに作った問題の `Cargo.toml`・`src/main.rs`・`main.cpp`・`main.py` は変わりません。

### 問題文の表示

- 問題文（日本語）・制限・数式が出ます。見出しの右に「input! を作る」「サンプルを保存」と「…」が並びます。「…」から、「再取得」（読み直す）・「公式ページ」（ブラウザに開く）・「この問題を作る」を選びます。見出しの行に出すものは、設定の画面の「問題文」で選べます。
- 画像は表示しません。画像のあった場所に「［画像があります。公式ページで見てください］」と出ます。
- 読めないとき（ネットワークが切れている、ページの作りが変わったなど）は、理由と「公式ページを開く」「もう一度試す」が出ます。

### input! を作る

- 問題文の欄の「input! を作る」で、問題文の「入力」の形式と「制約」から、proconio の `input!` の中身を作ります（保存してある問題文を使い、取得し直しません）。
  - 整数は、制約で負の値がありうれば `i64`、0 以上なら `usize`、制約から決められなければ `i64`（注意が出ます）。文字列は `Chars`、1 文字は `char`、実数は `f64`。
  - 名前は変数の名前を小文字にしたものです（縦に並ぶ組は、つないだもの。`X_i Y_i` なら `xy`）。Rust の予約語と同じになるときは、末尾に `_` を付けます（`fn_`・`if_` など。注意が出ます）。
  - 作った形で入力例を読んでみて、合うかを確かめます。合わないときは「入力例 N と合いません（…）」が出ます。
  - テストケースが複数の問題は、`main()` 用（`t: usize`）と `solve()` 用（1 ケース分）に分けて作ります。
  - クエリ（`query_1 … query_Q`）や読めない形式は、そこまでを作り、残りはコメントと注意で知らせます。
- 「solve() の input! を置き換える」：エディタで開いている `.rs` のファイルの `fn solve` の中の最初の `input! { … }` の中身を置き換えます（なければ `fn solve` の先頭に入れます）。⌘Z で戻せます。テストケースが複数なら、`main()` の `input!` も `t: usize` にします（`main()` に `input!` がなければ変えません。`for _ in 0..t { solve(); }` は自分で書きます）。設定の画面の「問題文」で「テストケースが複数のとき、main() に for も書く」を入にすると、`main()` に `input!` がなければ先頭に入れ、`main()` の中の `solve();` を `for _ in 0..t { solve(); }` にします（すでに `for` などの中で呼んでいれば、そのままにします）。
- 「コピー」：作ったものを写します。`fn solve` がないファイルでは、こちらを使います。
- 設定の画面の「問題文」で「問題を作るときに input! を入れておく」を入にすると、「コンテストを作る」「この問題を作る」で `main.rs` を書くときに、テンプレートの `fn solve` の `input!` を作ったものにしておきます（テストケースが複数なら「main() に for も書く」に従います）。作った結果の知らせに、問題ごとに「input! を入れました」（一部だけ・入力例と合わないものがあるときは添えます）か「input! を作れませんでした（理由）」が出ます。作れなかった問題と、すでにある `main.rs` は、そのままです。
- 生成した型・形は、問題文と見比べて確かめてください（入力例と合っても、型が正しいとは限りません）。
- **C++**：選んでいる問題の `<コンテスト>/<問題>/` が C++ のパッケージなら（なければ、設定の「問題を作るときの言語」が C++ なら）、ボタンは「入力のコードを作る」になり、宣言と `cin >>` の行を作ります。

  ```cpp
  long long N;
  cin >> N;
  vector<long long> A(N);
  for (auto& a : A) cin >> a;
  vector<long long> X(N), Y(N);
  for (int i = 0; i < N; i++) cin >> X[i] >> Y[i];
  ```

  - 整数はすべて `long long`、実数は `double`、1 文字は `char`、文字列は `string` です。名前は問題文のままです（`N`・`A`）。縦に並ぶ組は列ごとの `vector` にします。C++ の予約語と同じ名前には、末尾に `_` を付けます。
  - 「solve() の入力を置き換える」：開いている C++ のファイルの `solve()`（なければ `main()`）に、`// 入力（AtCoder Studio）` と `// 入力ここまで` の目印で囲んで書きます。目印があればその間を置き換え、なければ関数の先頭（`main()` なら `ios::sync_with_stdio(false);`・`cin.tie(nullptr);` の後）に入れます。⌘Z で戻せます。
  - テストケースが複数の問題は、`solve()` が要ります。`main()` に `T` を読むコードを入れ、「main() に for も書く」が入なら、`main()` の `solve();` を `for (int i = 0; i < T; i++) solve();` にします。
  - 「問題を作るときに input! を入れておく」が入なら、C++ の `main.cpp` にも同じように入れます。
- **Python**：選んでいる問題のパッケージが Python なら（なければ、設定の「問題を作るときの言語」が Python なら）、ボタンは「入力のコードを作る」になり、行ごとに `input()` で読む行を作ります。

  ```python
  N, M = map(int, input().split())
  A = list(map(int, input().split()))
  X = [0] * M
  Y = [0] * M
  for i in range(M):
      X[i], Y[i] = map(int, input().split())
  S = [input() for _ in range(N)]
  ```

  - 整数は `int`、実数は `float`、文字列と 1 文字はそのまま（`str`）です。間なしの格子は行ごとの文字列のリスト（`C[i][j]` で 1 文字）、間ありの格子はリストのリストです。名前は問題文のままです。縦に並ぶ組は列ごとのリストにします。Python の予約語と、作るコードで使う名前（`input`・`int`・`map`・`list`・`range` など）と同じ名前には、末尾に `_` を付けます。
  - 入力例で確かめるときは、行の分かれ方（1 行の値の数、横の列の長さ、縦の並びの行の数）も見ます。合わないときは「入力例 1 と合いません（2 行目：…）」のように出ます。
  - 「solve() の入力を置き換える」：開いている `.py` の `def solve():`（なければ `def main():`）に、`# 入力（AtCoder Studio）` と `# 入力ここまで` の目印で囲んで書きます。目印があればその間を置き換え、なければ関数の先頭に入れます（中身が `pass` だけなら、それと置き換えます）。⌘Z で戻せます。
  - テストケースが複数の問題は、`def solve():` が要ります。`main()` に `T = int(input())` を入れ、「main() に for も書く」が入なら、`main()` の直下の `solve()` を `for _ in range(T):` の中にします。
  - 「問題を作るときに input! を入れておく」が入なら、`main.py` にも同じように入れます。

## 実行とテスト

### 実行の対象

- 開いている `.rs` のファイルから、どのパッケージのどのバイナリを動かすかを決めます。決まらないファイルを開いているときは、直前の対象を使い続けます。
- `Cargo.toml` のないフォルダの `main.cpp` か、そのフォルダの `test/` の中のファイルを開くと、そのフォルダが C++ の対象になります（[C++](#c)）。同じフォルダに `Cargo.toml` もあれば Rust です。
- `Cargo.toml`・`main.cpp` のないフォルダの `main.py` か、そのフォルダの `test/` の中のファイルを開くと、そのフォルダが Python の対象になります（[Python](#python)）。
- 対象のパッケージのフォルダ名が問題 ID の形（例：`abc480_a`）なら、問題もそれに決まります。

### テストケースのフォルダ

| 置き場所 | 使うとき |
|---|---|
| `test/<バイナリ名>/` | あれば、いつも |
| `test/` | バイナリが 1 つのパッケージのとき（「コンテストを作る」で作ったパッケージはこちら） |

フォルダに置くファイル：

| ファイル | 使い方 |
|---|---|
| `sample-N.in`・`sample-N.out` | サンプルテストの入力と期待出力（N は 1 から） |
| `input.txt` | 「実行」の標準入力。なければ空の標準入力で動かします |
| `compare.json` | 比べ方と制限（下） |
| `random-N.in`・`random-N.out` | ランダムテストで失敗したケース（IDE が保存します） |
| `interactive-N.in` | 対話テストで、ジャッジに渡すケース |

### 実行・サンプルテスト

- 「実行」（⌘R）：`cargo build --release` でビルドし、`input.txt` を標準入力にして動かします。出力は「実行ログ」に出ます。
- 「サンプルテスト」（⇧⌘R）：`sample-N`（と `random-N`）をすべて動かし、「テスト結果」に判定・時間・メモリを出します。入力・期待する出力・実際の出力を並べて見られます。
  - 「このケースだけ実行」「失敗したケースだけ再実行」「このケースをデバッグ」「出力を期待出力として保存」のボタンがあります。
- 実行中のボタンは「停止」（⌘.）になります。
- ビルドに失敗したときは「エラー一覧」に出ます。行を押すと、その場所へ移ります。
- 判定は手元の規則で、ジャッジと同じ結果になるとは限りません。実行ログに、手元とジャッジの Rust の版が出ます。

### C++

`main.cpp` のあるフォルダ（例：`abc480/abc480_a/main.cpp`）を、C++ の 1 問として扱います。テストケースのフォルダ（`test/`）は Rust と同じです。

- 要るもの：Homebrew の GCC（`brew install gcc` で入る `g++-15`）。Apple の clang（Xcode の Command Line Tools の `clang++`）では、`#include <bits/stdc++.h>` が使えないため使いません。
  - 探す順：`settings.json` の `cpp.compiler`（g++ の絶対パス）→ `/opt/homebrew/bin/g++-15` → `PATH` の `g++-15` → `/usr/local/bin/g++-15`。
- 「実行」「サンプルテスト」：`g++-15 -std=gnu++23 -O2 -Wall -Wextra -DATCODER -DONLINE_JUDGE …` でビルドし、パッケージの `target/main` を動かします。オプションはジャッジの「C++23 (GCC 15.2.0)」に合わせています。ジャッジと違い、`-march=native`・`-fopenmp` などと、Boost などのライブラリは付けません（実行ログに出ます）。
- コンパイルのエラー・警告は「エラー一覧」に出て、押すとその行へ移ります。
- C++ の色分けは、`.cpp`・`.cc`・`.cxx`・`.hpp`・`.hh`・`.h` のファイルです。
- AC Library：アプリのフォルダの `libraries/ac-library/atcoder/` にあれば、ビルドで読みます（`#include <atcoder/all>` など）。ジャッジと同じ 1.6 を、[GitHub の atcoder/ac-library](https://github.com/atcoder/ac-library)（ライセンスは CC0）から取って、`atcoder/` のフォルダをそこに置いてください。実行ログの初めに、読む場所（なければ「なし」）が出ます。
- 問題・コンテストを作るときに C++ を選べます（[コンテストを作る](#コンテストを作る)）。
- 提出できます。言語は「C++23 (GCC 15.2.0)」です（[提出](#提出)）。
- 補完などの言語機能は clangd です（[エディタと言語サーバー](#エディタと言語サーバー)）。
- デバッグできます（[デバッグ](#デバッグ)）。
- ランダムテスト・対話テストができます。生成器・愚直解・ジャッジは `examples/gen.cpp`・`examples/naive.cpp`・`examples/judge.cpp`（`main_gen.cpp` などの名前でも使えます）です（[ランダムテスト](#ランダムテスト)・[対話テスト](#対話テスト)）。
- 問題文の欄で、入力のコード（宣言と `cin >>`）を作れます（[input! を作る](#input-を作る)）。

### Python

`main.py` のあるフォルダ（例：`abc480/abc480_a/main.py`）を、Python の 1 問として扱います。テストケースのフォルダ（`test/`）は Rust と同じです。同じフォルダに `Cargo.toml` や `main.cpp` もあるときは、そちらの言語になります。

- 処理系は、ジャッジの「Python (CPython 3.13.7)」か「Python (PyPy 3.11-v7.3.20)」に合わせます。設定の画面（⌘,）の「Python」の「処理系」か、`settings.json` の `python.interpreter`（`cpython`〔既定〕・`pypy`）で選びます。
- 要るもの：CPython は `python3.13`（`brew install python@3.13`）、PyPy は `pypy3.11` か `pypy3`（`brew install pypy3.11`）。IDE は入れません。
  - 探す順：`settings.json` の `python.cpython`・`python.pypy`（処理系の絶対パス）→ `/opt/homebrew/bin` → `PATH` → `/usr/local/bin`。
  - ジャッジと同じ版（CPython は 3.13、PyPy は Python 3.11 の版）でなければ、入れ方を出して動かしません。細かい版（3.13.7 と 3.13.15 など）の違いは、実行ログに出して動かします。
- 「実行」「サンプルテスト」：`python3.13 -E -B -X int_max_str_digits=0 main.py` のように動かします（`-X int_max_str_digits=0` はジャッジと同じ。`-E` で `PYTHONPATH` などの環境変数を読ませず、`-B` で `__pycache__` を作りません）。ビルドはありません。
- 動かす前に構文を確かめます。誤りがあると CE になり、「エラー一覧」から行へ移れます。
- `.py` のファイルは Python の色分けになります。
- ランダムテスト・対話テストができます。生成器・愚直解・ジャッジは `examples/gen.py`・`examples/naive.py`・`examples/judge.py`（`main_gen.py` などの名前でも使えます）です。
- 「コンテストを作る」「この問題を作る」で Python のパッケージを作るには、設定の画面の「問題文」で「問題を作るときの言語」を Python にします（[コンテストを作る](#コンテストを作る)）。
- 提出できます。言語は、設定の処理系に合わせて「Python (CPython 3.13.7)」か「Python (PyPy 3.11-v7.3.20)」です（[提出](#提出)）。
- 補完などの言語機能は basedpyright です（[エディタと言語サーバー](#エディタと言語サーバー)）。
- デバッグは debugpy です（[デバッグ](#デバッグ)）。
- 問題文から入力のコードを作れます（[input! を作る](#input-を作る)）。
- スニペットが使えます（[スニペット](#スニペット)）。

### compare.json

テストケースのフォルダに置きます。書かない項目は既定値です。「コンテストを作る」「この問題を作る」で作ったパッケージには、問題から決めた内容で最初から入っています（時間の制限は問題の制限＋500 ms、メモリは問題の値。問題文に「どれを出力しても正解」など答えが複数ありうる書き方があれば `none`〔目視確認〕、そうでなく「出力」に「誤差が 10^{-k} 以下」とあれば `float` と `1e-k`）。読み違えていたら、手で直してください。

- 答えが複数ありうる問題で、`whitespace` のままだと、正しい別の答えも AC 以外になり、提出の前のサンプルテストで止まります。そのときは `"mode": "none"` にします（目視確認のケースがあると、提出の前のテストは止めずに、確認のダイアログを出します）。設定の画面の「提出」で、提出の前のサンプルテストを切ることもできます。

```json
{ "mode": "float", "abs": 1e-6, "rel": 1e-6, "timeLimitMs": 2500, "memoryLimitMiB": 1024, "randomCount": 100 }
```

| 項目 | 意味 | 既定 |
|---|---|---|
| `mode` | `whitespace`（空白・改行の違いを無視）、`exact`（完全一致）、`float`（`abs`・`rel` の誤差の範囲で正解）、`none`（比べない） | `whitespace` |
| `abs`・`rel` | `float` のときの絶対誤差・相対誤差（少なくとも一方） | なし |
| `timeLimitMs` | サンプルテスト・ランダムテスト・対話テストの時間の制限（60000 まで。対話テストは、やり取りの全体にかける） | 2500 |
| `memoryLimitMiB` | メモリの制限（65536 まで）。実行中も見ていて、超えたらその場で止めて MLE にします | 1024 |
| `randomCount` | ランダムテストの回数（1〜10000） | 100 |

### ランダムテスト

- 同じパッケージの `examples/` に、生成器 `examples/<バイナリ名>_gen.rs` と愚直解 `examples/<バイナリ名>_naive.rs` を置きます（バイナリが 1 つなら `examples/gen.rs`・`examples/naive.rs` でも使えます）。
- C++ では `examples/gen.cpp`・`examples/naive.cpp`（`examples/main_gen.cpp`・`examples/main_naive.cpp` でも使えます）を、提出用と同じオプションでビルドします（パッケージの `target/examples/` に置きます）。
- 生成器には、回ごとの seed（整数）が 1 つ目の引数で渡ります。その seed から入力を作って標準出力に出してください。
- 「ランダムテスト」を押すと、`randomCount` 回まで、解答と愚直解の出力を比べます。最初に合わなかった回で止まり、そのケースを `random-N.in`・`random-N.out` として保存します（次のサンプルテストでも動きます）。

### 対話テスト

- ジャッジ（問題の相手役）を `examples/<バイナリ名>_judge.rs`（バイナリが 1 つなら `examples/judge.rs`）に置きます。C++ では `examples/judge.cpp`（`examples/main_judge.cpp` でも使えます）です。
- 「対話テスト」を押すと、解答とジャッジの標準入出力をつないで動かします。テストのフォルダの `interactive-N.in` があれば、そのパスがジャッジの 1 つ目の引数で渡ります（なければ引数なしで 1 回だけ）。
- 判定：両方が 0 で終われば AC、ジャッジが 0 以外で終われば WA、解答が異常に終われば RE、全体が `timeLimitMs` を超えれば TLE、解答のメモリが `memoryLimitMiB` を超えれば MLE。やり取りは「テスト結果」に時系列で出ます。
- 解答は、出力のたびに flush してください（しないと、ジャッジが待ち続けることがあります）。

## デバッグ

- エディタの行番号の左を押すか、F9 でブレークポイントを置き、「デバッグ」（F5）を押します。`input.txt`（「テスト結果」の「このケースをデバッグ」なら、そのケースの入力）を標準入力にして動かします。
- 止まると、その行が強調され、サイドバーが「実行とデバッグ」に切り替わって、変数・ウォッチ式・コールスタック・ブレークポイントが出ます（デバッグを始めたときに切り替わります）。
- 操作：続行・一時停止（F5）、ステップオーバー（F10）、ステップイン（F11）、ステップアウト（⇧F11）、止める（⌘.）。panic でも止まります。
- 下の「デバッグコンソール」で、式や LLDB のコマンドを打てます（あなたの権限で動きます）。
- デバッグするプログラムは、IDE の「書類」などへのアクセスの許可を引き継いで動きます（問題ごとに macOS の確認が出ないように）。
- デバッグは、最適化なし（dev）のビルドで動かします。ジャッジ（release）とは速さや、オーバーフローのときの動きが違います。
- C++ でもデバッグできます。`g++ -g -O0 -D_GLIBCXX_ASSERTIONS` でビルドし（パッケージの `target/main-debug`）、変数（`vector`・`string` なども）を見られます。ブレークポイントは `.cpp`・`.hpp`・`.h` などに置けます。
  - panic の代わりに、例外を投げたとき（`throw`）と `abort` で止まります。`-D_GLIBCXX_ASSERTIONS` で、`vector` の範囲外の読み書きなども `abort` になって止まります（実行・サンプルテスト・提出のビルドには付けません）。
  - 止まったときは、作業領域のソースのいちばん上のフレームが選ばれます。
  - デバッグコンソールに、LLDB の「`DW_TAG_member '_M_local_buf' refers to type …`」という警告が出ることがあります。GCC のデバッグ情報を LLDB が読むときのもので、変数の表示には影響しません。
- Python でもデバッグできます。debugpy を使い、設定の処理系（CPython・PyPy のどちらでも）で動かします。ブレークポイントは `.py` に置けます。
  - 要るもの：debugpy。IDE は入れません。初めてデバッグするときに、入れる命令が実行ログに出るので、ターミナルで実行してください（処理系ごとに、アプリのフォルダの `python/cpython`・`python/pypy` に入れます）。例：`"/opt/homebrew/bin/python3.13" -m pip install --target "$HOME/Library/Application Support/io.github.ishigaki892.acdstudio/python/cpython" debugpy`
  - 捕まえていない例外（`KeyError`・`IndexError` など）で、その行で止まります。`exit()`・`sys.exit()` では止まりません。
  - debugpy の中で動かすので、ふつうの実行よりかなり遅くなります。
  - デバッグコンソールでは、Python の式を打てます（LLDB のコマンドはありません）。

## エディタと言語サーバー

- `.rs` のファイルを開くと、rust-analyzer が動き、補完・診断・ホバー・インレイヒントが出ます。「コンテストを作る」で作ったコンテストのフォルダの中では、そのフォルダの問題をまとめて扱うので、同じコンテストの問題を行き来しても起動し直しません（問題を足したときは、起動し直します）。
- C++ のパッケージ（`main.cpp` のあるフォルダ）の `.cpp`・`.hpp`・`.h` などを開くと、clangd が動き、同じことができます。
  - 要るもの：Xcode の Command Line Tools の clangd（`xcode-select --install` で入ります）と、ビルドに使う g++（[C++](#c)）。
  - IDE が clangd に、ビルドと同じオプション（`-std=gnu++23`・`-DATCODER`・AC Library の場所など）を渡します。標準ヘッダーは使う g++ のものを読むので、`#include <bits/stdc++.h>` がエラーになりません。
  - `<コンテスト>/<問題>/` の形のフォルダでは、同じコンテストの C++ の問題をまとめて扱います。
  - clangd は、パッケージに索引（`.cache/`）を作らず、`.clangd` の設定ファイルを読みません。
  - 整形の書き方は `.clang-format` です。C++ でコンテスト・問題を作ると、コンテストのフォルダに置きます（LLVM の書き方で、字下げ 4）。ないフォルダでは、clangd の既定（字下げ 2）になります。
  - Rust のファイルと C++ のファイルを行き来すると、言語サーバーが起動し直します（動かすのはどちらか 1 つです）。
- Python のパッケージ（`main.py` のあるフォルダ）の `.py` を開くと、basedpyright が動き、補完・診断・ホバー・インレイヒント・定義ジャンプ・参照検索ができます。
  - 要るもの：basedpyright（ターミナルで `brew install basedpyright`）。IDE は入れません。
  - 設定の処理系（[Python](#python)）の版で調べます。型の検査の強さは basedpyright の `standard`（pyright の既定）で、開いているファイルだけを調べます。
  - `<コンテスト>/<問題>/` の形のフォルダでは、同じコンテストの Python の問題をまとめて扱います。
  - 整形（⇧⌥F・⌘S での整形）はしません（basedpyright に整形の機能がないためです）。⌘S は保存だけです。
  - Rust・C++ と同じく、言語を行き来すると言語サーバーが起動し直します。
- 定義へジャンプ（F12）、参照検索（⇧F12。Esc で閉じる）、整形（⇧⌥F。⌘S でも整形してから保存）。
- 標準ライブラリ・依存クレート、C++ の標準ヘッダー（使う g++ と SDK のもの）・AC Library、Python の型の情報（basedpyright の typeshed の `.pyi`）・標準ライブラリ・site-packages（設定の処理系のもの）へのジャンプは、読み取り専用のタブで開きます。
- 同じ名前のファイルを複数開くと、タブに見分けられるフォルダの名前（例：`…/abc339_a`）が添えられます。全体の場所は、タブにマウスを乗せると出ます。タブが並びきらないときは、タブの列の上でホイールを回すと横に送れます。
- タブの列の下のパンくずリストに、作業領域からのフォルダの道筋とファイルの名前、カーソルのある記号とそれを囲む記号が出ます（例：`abc480 › a › src › main.rs › impl Foo › bar`）。
  - 記号は言語サーバー（rust-analyzer・clangd・basedpyright）から聞きます。編集が止まって 0.5 秒ほどで新しくなります。言語サーバーが動いていないとき（信頼していないフォルダなど）は出ません。
  - Markdown（`.md`）では、見出しが出ます（`#` で始まる見出しの行だけ。コードの囲みの中は除きます）。
  - 段を押すと一覧が出ます。フォルダの段はそのフォルダの中身、ファイルの段は同じフォルダの中身（フォルダを選ぶとその中身に替わり、ファイルを選ぶと開きます）、記号・見出しの段は同じ段の記号・見出しの一覧（選ぶとその場所へ移ります）。↑↓ で選び、Enter で決め、Esc で閉じます。
  - 読み取り専用のタブは、ファイルの名前だけです。設定の「表示」で隠せます。
- 行頭のインデントは、段（4 スペース、またはタブ 1 つ）ごとに薄い色で塗られます。
- エラー・警告のある行は、背景に色が付き、行末にメッセージが出ます（いちばん重いもの。ほかにもあれば「（ほか N 件）」）。
- 調子が悪いときは、メニューの「ファイル」→「言語サーバーを再起動」。
- ファイルは自動で保存されます（⌘S ですぐ保存）。ほかのプログラムでファイルが変わったときは、「再読み込み」か「上書き」かを聞かれます。
- 保存できないファイル（ほかのプログラムで消された・書き込めないなど）があると、タブを閉じる・終了する・別のフォルダを開くときに、変更を捨てるかを聞かれます。

## スニペット

- アプリのフォルダ（[データの場所](#データの場所)）の言語ごとのファイルに、VS Code と同じ書き方でスニペットを書くと、その言語のファイルで使えます（ほかの言語のファイルでは出ません）。コメント（`//`・`/* */`）と末尾のカンマも書けます。
  - Rust：`snippets-rust.json`（`.rs` のファイル）
  - C++：`snippets-cpp.json`（`.cpp`・`.hpp`・`.h` などのファイル）
  - Python：`snippets-python.json`（`.py` のファイル）
  - 前の版の `snippets.json` は、`snippets-rust.json` がなければ、IDE が読むときに `snippets-rust.json` に名前を変えます。

  ```json
  {
    "入力を読む": {
      "prefix": ["rd", "読む"],
      "body": ["let ${1:n}: usize = sc.next();", "$0"],
      "description": "1 つ読む"
    }
  }
  ```

- 呼び出す文字（`prefix`）を打つと、補完の候補に ✂ の印で出ます。Tab か Enter で展開し、Tab・⇧Tab で欄（`$1`・`${1:既定の文字}`）を移ります。最後は `$0` の位置に移ります。2 行目からは、入れた行のインデントに合わせます（行頭のタブは 4 スペース）。
- 言語サーバーが動いていなくても、信頼していないフォルダでも使えます。
- ファイルを書き換えたら、IDE の窓に戻ると読み直されます。読めない項目は名前つきで知らせ（ほかは使えます）、JSON として読めないときは、前のスニペットのまま知らせます。
- 設定の画面（⌘,）の「スニペット」に、言語ごとに、今読めているスニペットの一覧が出ます。「ファイルを開く」でその言語のファイルを既定のテキストエディタで開きます（なければ空のものを作ります）。
- 「VS Code から取り込む」で、VS Code のその言語のスニペット（`~/Library/Application Support/Code/User/snippets/` の `rust.json`・`cpp.json`・`python.json`）を、言語のファイルに写します。確認のダイアログが出て、今のファイルは同じフォルダに `snippets-rust.backup-<時刻>.json`（C++ は `snippets-cpp.backup-…`、Python は `snippets-python.backup-…`）として退避します（言語ごとに、新しいものから 5 つまで残します）。VS Code のファイルを自動で読むことはありません。
- 選択肢（`${1|a,b|}`）は最初の候補を既定の文字にします。変数（`$TM_SELECTED_TEXT` など）は空になります。本文の中の文字としての `${`・`#{` は、欄として読まれます（書けません）。

## 提出

- 右下の「提出結果」の「ログイン」で、AtCoder のログインの窓が開きます。そこでログインしてください（パスワードは IDE に渡りません。ログインのセッションは macOS のキーチェーンに置きます）。
- 開催期間中の問題で「提出」を押すと、まずサンプルテストが動きます（「テスト結果」に出ます）。すべて AC のときだけ、次に進みます。AC でないケースがある・止めたときは送りません。サンプルのケースがない問題（対話の問題など）では、テストをせずに次に進みます。
- そのあと、提出の前の検査をして、確認のダイアログが出ます。「提出する」を選んだときだけ送ります。
  - Rust：別ファイルの `mod`、ジャッジにないクレート、版の違い、バイナリと問題の記号の違い。
  - C++（`main.cpp`）：自分のヘッダーを読む `#include "…"`、手元の GCC の版がジャッジ（15.2.0）と違うこと。
  - Python（`main.py`）：同じフォルダの自分のモジュール（`lib.py`・`lib/` など）や相対の `import`、ジャッジの言語の一覧にないパッケージの `import`（PyPy は CPython より少なく、`numba` などがありません）、手元の処理系の版がジャッジ（CPython 3.13.7・PyPy 7.3.20）と違うこと。`import` は手元の処理系で読みます（文字列・コメントの中は数えません）。処理系が見つからないときは、確かめていないことを注意に出します。
    - ジャッジのパッケージは、言語の一覧のパッケージ名を `import` の名前にして比べます（`scikit-learn` は `sklearn`、`ac-library-python` は `atcoder`、`z3-solver` は `z3` など）。一覧にない、ほかのパッケージの依存として入っているもの（PyPy の `dateutil` など）にも注意が出ることがあります。
- 言語は、提出のページの選択肢から選びます。Rust は「Rust」で始まる最初のもの、C++ は「C++23 (GCC 15.2.0)」、Python は設定の処理系に合わせて「Python (CPython 3.13.7)」か「Python (PyPy 3.11-v7.3.20)」です（ないときは送りません。Codon は選びません）。
- 設定の画面の「提出」で、次の 2 つを変えられます（[設定](#設定)）。
  - 提出の前のサンプルテスト（初めはオン）。オフにすると、テストを動かさずに次に進みます。
  - 確認のダイアログ（初めは出す）。出さないようにしても、省くのは、今のソースのサンプルテストがすべて AC で、提出の前の検査の注意がないときだけです（サンプルがない・目視確認のケースがある・テストのあとでファイルを変えた・注意があるときは出ます）。省いたときは、実行ログに「確認のダイアログを省いて提出しました」と出ます。出さないようにして保存するときは、OS の確認が出ます。
  - サンプルテストが通ったかは、IDE が実行履歴で確かめます。
- 送ったあとは「提出結果」に判定が出て、確定まで追います。「更新」で読み直し、「詳細」で公式の詳細ページを開きます。
- 期間の外の問題では送りません。「コードをコピーして公式の提出ページを開く」で、ブラウザから提出できます。
- 「提出」のキーは、初めは割り当てていません（[キーの割り当て](#キーの割り当て)）。

### コンテストの提出状況

- アクティビティバーの「コンテスト」（旗）で、問題文の欄の問題のコンテストについて、問題ごとの提出状況が出ます。開いているファイルを替えて問題が替わると、コンテストも替わります。
  - ✓（緑）：AC の提出がある。✗：提出はあるが AC がない（最後の判定と回数を出します）。・：提出がない。
- AtCoder の「自分の提出」のページ（そのコンテストのものだけ）を、ログインのセッションで読みます。読むのは、「コンテスト」を開いたとき（前に読んでから 1 分たっていれば）・コンテストが替わったとき・「更新」を押したとき・ログインしたときだけです。ページは 1 秒ずつあけて、新しいほうから 10 ページまで読みます（超えたら知らせます）。
- IDE から出した提出は、通信せずに行に重ねます（判定を追っている間の表記も出ます）。
- 行を押すと、問題文の欄でその問題を選びます。パッケージのフォルダから決まった問題と紐付いているときは、紐付けを外してその問題を出します（問題の選択欄の「フォルダの問題に戻す」で戻ります）。
- ログインしていないときは「ログイン」ボタンが出ます。読めなかったときは理由が出て、前の結果は残ります。
- 「自分の提出を開く」で、公式のページを既定のブラウザで開きます。

## キーの割り当て

| 操作 | キー | `command` |
|---|---|---|
| サイドバー | ⌘B | `toggleSidebar` |
| 保存 | ⌘S | `save` |
| タブを閉じる | ⌘W | `closeTab` |
| フォルダを開く | ⌘O | `openFolder` |
| 実行 | ⌘R | `run` |
| サンプルテスト | ⇧⌘R | `test` |
| 停止 | ⌘. | `stop` |
| 定義へジャンプ | F12 | `goToDefinition` |
| 参照検索 | ⇧F12 | `findReferences` |
| 整形 | ⇧⌥F | `formatDocument` |
| デバッグ・続行 | F5 | `debug` |
| ブレークポイント | F9 | `toggleBreakpoint` |
| ステップオーバー | F10 | `stepOver` |
| ステップイン | F11 | `stepIn` |
| ステップアウト | ⇧F11 | `stepOut` |
| 提出 | （なし） | `submit` |
| 設定 | ⌘, | `openSettings` |
| エクスプローラー | ⇧⌘E | `showExplorer` |
| 検索 | ⇧⌘F | `showSearch` |
| 実行とデバッグ | ⇧⌘D | `showDebug` |

- 割り当ては、アプリのフォルダの `settings.json` の `keyBindings` の一覧で変えます（[設定](#設定)）。一覧に書いたコマンドはその割り当てを使い、書いていないコマンドは既定の割り当てを使います。変えたら、IDE の窓に戻ると読み直されます（起動し直さなくてよい）。
- 1 つの割り当ての書き方（`meta` は ⌘、`alt` は ⌥）：

  ```json
  { "command": "submit", "key": "enter", "meta": true, "ctrl": false, "alt": false, "shift": true }
  ```

- `key` は、キーの名前（英字は小文字。例：`r`、`.`、`f12`、`enter`）です。⌥ を使う割り当ては、英字・数字ならキーの位置でも合わせます。
- キーを外すときは、`"key": ""` と書きます（既定の割り当ても使いません）。
- 読めない割り当てや知らないコマンドは使われず、ファイル一覧の下に知らせが出ます。同じキーを 2 つのコマンドに書いたときも知らせが出ます（一覧の先のものを使います）。
- ファンクションキーは、macOS の設定によって、そのまま押すと明るさなどの機能になることがあります。そのときは fn を押しながら押します。

## 設定

- ⌘,、メニューの「AtCoder Studio」→「設定…」、アクティビティバーの下端の歯車で、設定の画面が開きます。
  - 「キー」：コマンドごとに「変更」（押したキーを割り当てる。Esc でやめる）・「なし」・「既定に戻す」。ほかのコマンドと同じキー、⌘・⌃・⌥ を押さないキー（F1〜F20 は使えます）、macOS とメニューのキー（⌘C・⌘Z など）は割り当てられません。
  - 「色」：色を選ぶ欄と濃さ（0〜100%）、「既定に戻す」。
  - 「表示」：インデントの色・診断の行・パンくずリストの表示の入切、エディタと問題文の文字の大きさ。
  - 「問題文」：問題文の欄の見出しの行に出すボタン（出さないものは「…」の一覧に入ります）、問題を作るときの言語、問題を作るときに `input!`（C++・Python は入力のコード）を入れておくか、テストケースが複数のとき `main()` に `for` も書くか（[input! を作る](#input-を作る)）。
  - 「提出」：提出の前のサンプルテストと、確認のダイアログ（[提出](#提出)）。
  - 「Python」：`main.py` を動かす処理系（CPython 3.13・PyPy 3.11。[Python](#python)）。処理系のパスは `settings.json` で書きます。
  - 「スニペット」：今読めているスニペットの一覧、「ファイルを開く」「VS Code から取り込む」（[スニペット](#スニペット)。保存とは関係しません）。
  - 「テンプレート」：雛形のファイル（`templates/main.rs`・`templates/dependencies.toml`・`templates/main.cpp`・`templates/main.py`）があるかと、「テンプレートのフォルダを開く」（Finder で開きます。フォルダがなければ作ります。[雛形](#雛形)。保存とは関係しません）。
  - 色と表示は、変えるとすぐに画面に出ます。「保存」で `settings.json` に書き、「キャンセル」（または Esc）で元に戻ります。
  - 保存で書き換えるのは、キー・色・表示・問題文・提出の項目だけで、`settings.json` に自分で書いたほかの項目は残ります。キーは、すべてのコマンドの割り当てを書きます（同じコマンドに 2 つ以上書いていたときは、先のものだけになります）。
  - 画面を開いている間に `settings.json` を外で変えたときは、画面が読み直されます（保存はしません）。
- 画面の「JSON で開く」で、`settings.json` を既定のテキストエディタで開けます。書き換えて保存し、IDE の窓に戻ると読み直されます。JSON が崩れているときは、今の設定のまま使い、ファイル一覧の下に知らせが出ます（直して戻れば使われます。崩れている間は、設定の画面から保存できません）。
- 書き方（どの項目も、書かなければ既定の値です）：

  ```json
  {
    "version": 1,
    "keyBindings": [ … ],
    "colors": { "indent-rainbow-1": "rgba(255, 255, 64, 0.25)", "syntax-keyword": "#ff8080" },
    "editor": { "indentRainbow": true, "errorLens": true, "breadcrumbs": true, "fontSize": 13 },
    "problem": { "fontSize": 13, "buttons": ["makeInput", "saveSamples"], "mainLoop": false, "fillInput": false },
    "submit": { "testBeforeSubmit": true, "confirmDialog": true }
  }
  ```

  - `colors`：色の名前と、CSS の色（`#rrggbb`、`rgba(…)` など）。名前は `src/styles/tokens.css` の色の変数から先頭の `--` を除いたもの（例：`bg-base`、`syntax-keyword`、`indent-rainbow-1`、`lens-error-line`）。書いたものだけが変わります。
  - `editor.indentRainbow`・`editor.errorLens`・`editor.breadcrumbs`：インデントの色、診断のある行の色とメッセージ、パンくずリストの入切。
  - `editor.fontSize`・`problem.fontSize`：エディタと問題文の欄の文字の大きさ（8〜32 の整数、px）。
  - `problem.buttons`：問題文の欄の見出しの行に出すボタン。`makeInput`（input! を作る）・`saveSamples`（サンプルを保存）・`refresh`（再取得）・`openPage`（公式ページ）・`createProblem`（この問題を作る）。並びは書いた順ではなく、この順です。
  - `problem.fillInput`：「コンテストを作る」「この問題を作る」で `main.rs` を書くときに、`input!` を入れておくか（[input! を作る](#input-を作る)。Rust だけ）。
  - `problem.language`：問題・コンテストを作るときの言語（`rust`・`cpp`）。
  - `problem.mainLoop`：テストケースが複数のとき、「solve() の input! を置き換える」で `main()` に `input!` と `for _ in 0..t { solve(); }` まで書くか（[input! を作る](#input-を作る)）。
  - `submit.testBeforeSubmit`・`submit.confirmDialog`：提出の前のサンプルテストと、確認のダイアログ（[提出](#提出)）。手で `confirmDialog` を `false` にしたときは、OS の確認は出ません。
  - `cpp.compiler`：C++ に使う g++ の絶対パス。空なら探します（[C++](#c)）。
  - `python.interpreter`：Python の処理系（`cpython`・`pypy`）。`python.cpython`・`python.pypy`：処理系の絶対パス。空なら探します（[Python](#python)）。
  - 読めない項目は既定の値を使い、知らせが出ます。

## 既知の制限

- **⌃Space**：エディタの補完を手で出すキーですが、macOS の「入力ソースの切り替え」と重なっていると、入力ソースが切り替わります。補完は打っている間に自動で出ます。手で出したいときは、macOS の設定（キーボード → キーボードショートカット → 入力ソース）で、切り替えのキーを変えてください。
- **F11**：macOS の機能（デスクトップを表示など）と重なることがあります。ステップインに使うなら、macOS の設定で外すか、`settings.json` で `stepIn` のキーを変えてください。
- **Rust が見つからない**：「cargo が見つかりません」と出たら、[rustup](https://rustup.rs) で Rust を入れてください。
- **GCC が見つからない**：C++ で「g++-15 が見つかりません」と出たら、ターミナルで `brew install gcc` を実行してください。
- **clangd が見つからない**：C++ のファイルで「clangd が要ります」と出たら、ターミナルで `xcode-select --install` を実行してください。
- **basedpyright が見つからない**：`.py` のファイルで「basedpyright が要ります」と出たら、ターミナルで `brew install basedpyright` を実行してください。
- **ジャッジとの違い**：手元の判定・時間・メモリは目安です。ジャッジの版（rustc 1.89.0、edition 2024）は、AtCoder の言語の更新で変わることがあります。
- **提出**：参加の登録が要るコンテストで登録していないときの動きは、まだ確かめていません。提出する言語は、提出のフォームの選択肢のうち、Rust の最初のもの、C++ は「C++23 (GCC 15.2.0)」です（Rust の選択肢が複数ある場合の動きは、まだ確かめていません。C++ の Clang・IOI-Style では送りません）。
- **出力の末尾の改行**：サンプルテストの空白緩和（`whitespace`）は、AtCoder の公式の説明の文言どおり、期待出力が改行で終わるなら、出力も空白で終わることを求めます（`print!` で改行を出さないと AC 以外になります）。実際のジャッジがどう判定するかは確かめていません。
- **安全**：信頼したフォルダのコードは、制限なく（サンドボックスなしで）動きます。デバッグ中は、デバッグコンソールから LLDB のコマンドを使えます。ログインのセッションはキーチェーンに置きますが、同じ利用者のほかのプログラムが読める場合があります。
- **Windows**：対応していません。
